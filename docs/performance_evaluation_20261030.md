# 物流售后多 Agent 系统性能评估报告

- **评估日期**：2026-10-30
- **被测系统**：Project2_logistics_agent，FastAPI + LangGraph 七节点工作流 + SSE + 外部 LLM/RAG + SQLite
- **评估方式**：黑盒接口压测、SSE 节点计时、进程与系统资源采样、外部依赖独立探测
- **时区**：Asia/Shanghai（UTC+8）

> 本报告仅使用本次执行采集的数据。未提供生产 SLA、真实生产流量或既有容量基线，因此“峰值”指本次构造的阶梯负载，不声称代表生产真实峰值；“最高验证并发”不等于系统理论极限。

## 1. 执行摘要

**结论：系统需要优化，且应在扩大生产流量前优先处理外部检索可用性与完整 Agent 串行调用延迟。**

1. **本地接口响应快，完整 Agent 尾延迟高。** 核心场景中，健康检查、工单查询和复核 P50 分别为 2.0 ms、5.7 ms、23.4 ms；完整物流/退款/多轮退款合并 P50/P95/P99 为 **7.42/14.95/16.93 s**。
2. **本次 500 个正式请求均未失败，但成功不等于完整能力正常。** 核心 160、峰值 160、长稳 180 个请求的 HTTP 成功率和业务状态校验成功率均为 100%；然而峰值检索只呈现约 8 秒等待或毫秒级本地降级两类路径。首次独立 Embedding 探测发生 15.056 秒 `ReadTimeout`，第二次探测以 0.266 秒成功返回 1024 维向量，证明依赖存在间歇性波动，因此不能把 100% 成功解读为在线 RAG 始终正常。
3. **瓶颈不是本地规则计算或 CPU。** 峰值完整 Agent 的 80 个样本平均端到端耗时 11.34 s，其中知识检索平均 3.20 s（28.3%）；路由、信息抽取、工具选择、最终回复首 Token 与流式生成合计约 71.1%；本地风控、工单生成和回复组装合计不足 1%。40 并发时进程 CPU 最大 47.8%（100% 表示一个逻辑核），整机 CPU 最大 31.2%。
4. **40 并发已出现吞吐反降和轻量请求变慢。** 20 并发轮次吞吐 3.01 req/s，冷检索 40 并发轮次吞吐 2.23 req/s；FAQ 的 P50 从核心场景 0.041 s 增至 40 并发的 1.175 s。两轮检索状态不同，数值不能直接视作严格容量曲线，但 40 并发下完整链路 P95 17.80 s 的退化结论成立。
5. **30 分钟长稳未观察到内存泄漏或持续时延漂移。** 180/180 请求成功，三个时间窗口成功率均为 100%，混合 P95 为 15.094/15.149/15.343 s；RSS 从 111.34 MiB 降至 93.01 MiB，剔除前 5 分钟后的斜率为 -0.043 MiB/min，线程与句柄未增长。该结果用于识别趋势，不替代 8–24 小时或更长生产浸泡测试。

### 2.1 指标口径

- **e2e**：客户端发出请求到响应体完整结束。
- **TTFB**：收到响应头的时间。SSE 会提前返回响应头，因此用户感知应重点看首 Token 与 e2e，不能只看 TTFB。
- **首 Token**：首个 SSE `token` 事件到达时间。
- **HTTP 成功**：无传输异常且状态码为 2xx。
- **业务成功**：HTTP 成功，且 `done` 状态、转人工标志、FAQ 来源或工单状态符合用例预期，未出现已知服务降级文案。
- **HTTP 错误率**：传输异常或非 2xx 请求占比；**业务错误率**：未通过上述业务校验的请求占比。
- **分位值**：最近秩法，`rank=ceil(p×n)`。每个峰值级别仅 40 个总样本、每个完整 Agent 场景 20 个样本，其 P99 属探索性结果；核心聊天合并样本为 100，峰值完整 Agent 合并样本为 80。
- **资源**：进程 CPU/RSS/线程/句柄含子进程；100% 进程 CPU 表示一个逻辑核。Windows 进程 I/O 不是纯磁盘口径，因此另采整机磁盘；网卡与磁盘吞吐均为整机数据，含其他应用，不能归为被测进程独占。

## 7. 综合结论与优化优先级

### P0：恢复并验证外部 Embedding/RAG 正常路径

**依据：** 检索 P95 8.028 s；峰值完整 Agent 31/80 出现约 8 秒等待，其余主要为快速本地降级；两次独立 Embedding 探测分别为 15.056 s 超时和 0.266 s 成功，依赖波动已复现。

建议：

1. 检查本机到 DashScope 的网络、DNS/TLS、代理、配额和模型可用性，保留平台请求 ID 与错误码；不要简单延长超时掩盖问题。
2. 为 Embedding/Rerank 增加独立健康检查、成功率、超时率、熔断次数、降级次数与耗时指标；在 SSE `done` 中明确返回 `degraded` 和降级来源，避免将本地降级计为完整 RAG 成功。
3. 为检索依赖设置独立的小并发闸门与 single-flight，冷启动首次失败后立即熔断；40 并发中 17/20 路同时等待约 8 秒，说明当前熔断无法阻止首批并发超时。
4. 对静态政策查询增加有 TTL 的检索结果缓存，并限制缓存 key 与容量；订单/物流动态数据不可照搬该缓存。
5. 修复后重新执行相同核心与阶梯测试，分别报告“正常在线 RAG”和“降级 RAG”两套容量，不混用结果。

### P0：缩短完整 Agent 的串行模型链路

**依据：** 峰值完整 Agent 平均 11.343 s，路由、抽取、工具选择和最终生成合计约 71.1%；核心完整 Agent P95 14.954 s。

建议：

1. 将意图识别与信息抽取合并为一次结构化输出调用，减少一次串行网络往返。
2. 对订单号明确、意图高置信的场景采用确定性工具路由，直接调用订单/物流/退款资格工具；保留低置信场景的 LLM tool-calling 作为兜底。
3. 信息抽取完成后，政策检索与业务工具查询无数据依赖的部分并行执行，而不是固定串行经过所有节点。
4. 保留当前最终回复真流式机制，压缩重复上下文和不必要的政策片段，分别考核首 Token 与流式结束时间。
5. 优化后用同一数据集对比 P50/P95/P99、外部调用次数和业务正确率，不能只用平均耗时判断收益。

### P1：隔离重链路对轻量请求的影响，治理同步 I/O

**依据：** 40 并发 FAQ P50 从核心 0.041 s 升至 1.175 s，但本地风控和工单节点仍为毫秒级，CPU 未饱和。

建议：

1. 将同步 SQLite、Chroma 调用移出事件循环或改用异步访问；为外部调用与本地工具设置独立、有上限的线程池和连接池。
2. SQLite 开启 WAL、合理 `busy_timeout` 与事务边界，减少每次操作新建连接；为高并发写入设置背压，而非直接增加 Uvicorn worker 放大锁竞争。
3. 为 `chat_history(session_id, id)` 建索引，并在更长浸泡中观察历史表增长对查询的影响。
4. 对 FAQ/健康检查与完整 Agent 设置独立并发配额或隔离资源，防止重请求拖慢轻请求。

### P1：建立可发布的性能门禁

**依据：** 当前业务状态成功率为 100%，但检索降级未被业务失败口径捕获；不同峰值轮次的熔断状态显著影响吞吐。

建议：

1. 将指标拆为 HTTP 成功、业务状态成功、完整能力成功和降级成功，分别设置门禁。
2. 固定外部依赖状态并记录版本，每个并发级别至少重复 3 轮；关键场景分位值样本尽量不少于 100。
3. 在修复依赖后重新确定生产并发限额；当前 40 并发“无错误”不能直接转写为生产容量或 SLA。

### P2：延长浸泡并扩大数据规模验证

**依据：** 本轮约 30 分钟长稳未观察到泄漏，SQLite 仅增加 92 KiB，样本与数据规模不足以覆盖长期对象增长和大型历史表影响。

建议执行 8–24 小时浸泡，周期性采集 Python GC 对象、内存剖析和堆快照，并使用更接近生产规模的历史数据复测查询与写入时延。

## 8. 复现方法

在项目根目录执行，先准备 `.env` 并启动服务：

```powershell
.\.venv\Scripts\python.exe main.py
```

另开终端安装压测客户端依赖并执行：

```powershell
python -m pip install httpx==0.28.1 psutil==5.9.0
python -m src.evaluation.performance_test --mode core --repeat 20 --concurrency 2 --output evaluation_results/core-c2-n160.json
python -m src.evaluation.performance_test --mode load --requests 40 --concurrency 5 --output evaluation_results/peak-c05-n40.json
python -m src.evaluation.performance_test --mode load --requests 40 --concurrency 10 --output evaluation_results/peak-c10-n40.json
python -m src.evaluation.performance_test --mode load --requests 40 --concurrency 20 --output evaluation_results/peak-c20-n40.json
Start-Sleep -Seconds 65
python -m src.evaluation.performance_test --mode load --requests 40 --concurrency 40 --output evaluation_results/peak-c40-n40.json
Start-Sleep -Seconds 65
python -m src.evaluation.performance_test --mode soak --duration 1800 --rate 0.1 --concurrency 4 --output evaluation_results/soak-30min-r01.json
```

原始 JSON 包含每次请求、SSE 节点偏移、逐秒资源样本、运行配置、环境与汇总，可用于独立重算。正式样本排除 `smoke-core.json`。测试会写入聊天历史、工单与复核记录，不应直接对生产库执行。

## 10. 限制与后续验证

1. 测试在单台 Windows 工作站上执行，结果受本机其他进程、外部模型与网络状况影响，不代表生产服务器容量。
2. 未提供生产 SLA，因此报告不虚构“达标/不达标”线；优化结论基于实测时延、吞吐变化、依赖超时和资源数据。
3. 峰值每级样本量较小，P99 只作探索性参考；不同轮次熔断状态不同，吞吐不能作为严格单调容量模型。
4. 整机磁盘/网络包含其他应用，进程 I/O 也不是纯磁盘口径；不能据此做应用独占资源归因。
5. 30 分钟 RSS 趋势不能证明永久无泄漏；上线前仍建议执行 8–24 小时浸泡，并结合 Python GC 对象、内存剖析和堆快照定位。
6. 核心与峰值业务链路未观测到正常在线 Embedding 路径；长稳出现 4 次 0.317–0.439 s 的在线路径候选，但缺少服务端检索成功标记，且正常在线 RAG 样本仍不足。虽然独立复测已成功，正常 RAG + Rerank 的持续性能仍需在依赖稳定后补测。
